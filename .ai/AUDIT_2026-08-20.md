# LinguaChat quality closure audit — 2026-08-20

This is a measured pre-work audit. It records what the live repository supports,
what is stale or misleading, and the order in which defects should be removed.
Quality beats throughput. Voice/calls/video/STT/TTS/pronunciation remain out of
scope.

## Executive state

LinguaChat has a strong deterministic learning/QA foundation, but it is not yet a
finished all-level product. Pre-A1 is mature and frozen. A1 arcs 1–5 are merged;
arcs 6–7 and the final A1 availability gate remain. There is no authored A2–C2
curriculum blueprint in `docs/curriculum/` today, even though placement/missions
use A1–C2 labels.

The most immediate risk is not curriculum volume. It is truth drift between the
product, the backend and the autonomous-agent control plane.

## P0 — control plane / automation

1. `Claude — mention` run 32331959420 failed at 41 turns with
   `error_max_turns` (`--max-turns 40`), after successful checkout, OIDC and token
   setup. No remote branch survived.
2. The mention action is the wrong lane for LC-OPS-009: its GitHub capability
   contract explicitly refuses `.github/workflows` edits, while LC-OPS-009 is
   primarily workflow work. Do not blindly rerun it.
3. `claude-chain.yml` can merge from a QA `workflow_run`, but its `advance` job
   does not run in that same invocation; normal chaining therefore relies on a
   later event that a `GITHUB_TOKEN`-performed merge must not be assumed to emit.
4. No chain watchdog schedule exists. The two workers have independent weekly
   schedules instead, which duplicates routing/claim logic.
5. General/i18n workers do not both use `next-task.mjs` as the sole gate.
6. `claude-mention`, general worker and i18n worker do not share one writer lock.
7. QA does not explicitly listen for `ready_for_review`.
8. Mention runs have no equivalent of the autonomous worker's early-branch / final
   recovery discipline, so a turn ceiling can still mean zero surviving work.

Decision: LC-OPS-009 is first. Implement it through the ChatGPT GitHub connector
(which has workflow write permission), then validate through a PR and GitHub QA.
Use `@claude` for diagnosis/small changes only, not workflow infrastructure.

## P0 — source-of-truth drift

`CLAUDE.md`, `.ai/STATE.md`, `.ai/HANDOFF.md` and `.ai/TRANSLATIONS.md` are stale
and in one case product-wrong:

- Arc 5 is complete but several files still say arc 5/005d is pending.
- counts are stale (pre-Arc5 key/check counts).
- the old three-independent-language rule (`interface es + native ja + target en`)
  remains written as a requirement.

Owner-corrected product rule:

`user_language` is one choice. UI, explanations, hints, corrections,
interpretations and meanings use that same language. Target study language is
English. Legacy `interface_language` and `native_language` may remain temporarily
for migration compatibility, but must resolve to the same user choice.

Decision: after LC-OPS-009, true up all coordination files and add a consistency
check so stale control-plane prose cannot silently direct an agent again.

## P0 — product identity / privacy legacy

1. Frontend storage has already collapsed the visible companion choice to Lingua,
   but the backend still accepts `lingua|lingo|chatto`; the local engine still has
   Lingo-as-vocabulary-tutor and Chatto-as-conversation-tutor branches; the real
   OpenAI system prompt still describes the same obsolete roles.
2. A personal/demo user record is hardcoded in the public backend `app/db.py`.
3. Auth/user persistence is still demo/local/in-memory, not a production account
   system. This is acceptable while cloud persistence is deliberately postponed,
   but the UI/docs must not imply durable accounts.

Decision: remove the personal seed and close legacy companion behavior end to end
before any real provider is enabled or the app is presented as production-ready.

## P1 — i18n truthfulness

1. `services/language.js` exposes 46 selectable entries spanning 34 base
   languages; only 8 base locales currently exist (English + es/pt/fr/it/de/ja/ar).
   The other 26 bases normalize/fall back to English while looking selectable.
2. `i18n/translations.js` contains a second, conflicting `LANGUAGE_OPTIONS` list
   with only six languages and excludes ja/ar despite their real locale files.
3. `normalizeLocale()` explicitly maps an unsupported language to English. This is
   safe as a runtime fallback but dishonest if the picker labels the language as
   supported.
4. The local pedagogical chat engine is heavily Spanish-specific (Spanish
   translation dictionary, Spanish correction explanations, Spanish prompts), so
   100% interface-key coverage does not mean pedagogical parity for Japanese,
   Arabic, etc.
5. Placement questions, placement feedback/plan, and several profile strings are
   hardcoded Spanish/English rather than going through i18n.
6. RTL is effectively special-cased to Arabic in several surfaces; Hebrew,
   Persian and Urdu cannot be advertised until direction handling is generalized.

Decision: first make the picker honest and unify `user_language`; then repair all
8 existing languages end to end; only then add new locales in small tested batches.
Do not claim a language from a fallback.

## P1 — placement / level truth

Placement currently labels A1–C2 using 6–10 multiple-choice items and returns a
CEFR level/confidence. However:

- only Pre-A1 is open;
- A1 is partial/closed;
- no A2–C2 curriculum blueprint exists in `docs/curriculum/` today;
- `DEFAULT_PROFILE.level` is B1 and profile surfaces can display that label even
  though it is not a playable curriculum level;
- placement content and its feedback are hardcoded Spanish.

A proficiency estimate and a playable course level must become distinct concepts.
Until higher curricula exist, placement may estimate a level only if the UI
honestly says what course material is actually available. The current shallow test
must not be marketed as a high-confidence formal CEFR assessment without stronger
evidence.

## P1 — all-ages/safety claim

The product has `learner_style` choices for child/teen/adult/older_adult and the
real-model prompt has some age-tone guidance, but no dedicated content-safety /
age-appropriate moderation layer was found in the current backend AI surface.
Therefore the repo does not yet justify an unrestricted “all ages” production
claim. Add explicit safety behavior/tests before child support is called complete.

## P1/P2 — teaching quality

Strengths already present:

- Pre-A1 is frozen and repeatedly audited in browser/journey tests.
- adaptive scaffolding, learner facts, review scheduling, recovery and evidence
  semantics have dedicated checks;
- A1 arcs 1–5 were built against a written blueprint rather than ad hoc content;
- Arc 5 has a real production-browser walkthrough (happy path, wrong/retry,
  assistance, replay/no duplicate reward).

Remaining:

1. Build A1 Arc 6 (34–35) in small content/evaluator/copy/proof slices.
2. Build A1 Arc 7 (36–38) the same way.
3. Final A1 gate must test all 21 episodes and required capabilities and also solve
   the product-level selection problem: `playableLevelId()` currently returns the
   first available level, so simply flipping A1 `available:true` would not be a
   complete multi-level UX.
4. After A1, design A2 as a blueprint/authoring contract before implementation;
   then progress sequentially. Do not let the current A2–C2 placement/missions
   masquerade as authored curricula.

## P2 — QA gaps

Current deterministic coverage is unusually strong (50 frontend `check:all`
invocations after Arc 5; last merged backend evidence 444 pytest). But browser
proof is ad hoc through system Chromium, not a permanent automated E2E suite.

Before release quality is claimed:

- add stable browser smoke/regression coverage for the core learner journey at
  390px/1440px, light/dark and RTL;
- add i18n linter coverage for hardcoded visible copy, unsupported advertised
  languages, raw keys, placeholders/plurals and locale cross-contamination;
- add product-contract tests for Lingua-only tutoring and user-language parity;
- add control-plane consistency checks for TASKS/STATE/HANDOFF/TRANSLATIONS.

## P3 — cleanup / delivery truth

- `linguachat-frontend-old/` remains tracked legacy code.
- unrelated empty root files (`pacientes.txt`, `procedimientos.txt`) remain.
- README is explicitly “LinguaChat Local”, documents mock auth/flows and contains
  stale JourneyRail/mock descriptions.
- deploy/production persistence/auth are not finished. Supabase remains postponed
  by product decision, so this needs an honest non-Supabase deployment/persistence
  decision later rather than accidental scope creep now.
